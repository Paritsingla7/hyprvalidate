# hyprvalidate — build plan

Living document. Update this when scope changes, not just when code lands.

## What we're building

Two features, sharing one foundation:

1. **Validator** (primary, build first): reads an existing Hyprland Lua
   config — hand-written, or output from any of the existing converters —
   and reports every place it references a config key, dispatcher, or option
   that doesn't exist in the real Hyprland API, or gives a value of the
   wrong type. Then runs `luac -p` as a final syntax gate.
2. **Converter** (secondary, build after): turns an old `hyprland.conf`
   into Lua, the same job the four existing tools attempt — but with symbol
   names and value types looked up from the schema instead of guessed from
   the input string or hand-typed into a table.

Both are consumers of the same schema. Neither is useful without it.

## Why

Full research trail lives in the session history that produced this repo;
short version:

- Hyprland's real API surface (dispatchers, config keys, their types) is
  published by Hyprland itself, autogenerated from source, reinstalled on
  every build, present since the first Lua-capable release (v0.55.0) via an
  unconditional CMake install rule (`meta/hl.meta.lua` → `share/hypr/stubs/`).
- None of the four existing community converters read it correctly. Three
  don't try. The fourth (hypr2lua) loads the file and threads a `Schema`
  object through its whole pipeline, but its parser's line filter skips
  every line starting with `--`, which is every LuaLS annotation in the
  file — it extracts zero entries and nothing downstream ever reads the
  (empty) result anyway. Confirmed by reading the source, not guessing.
- Consequence: all four hand-transcribe dispatcher names and config keys
  into their own tables from memory/docs, and all four tables are wrong or
  incomplete in different ways (measured dispatcher-table sizes: 53, 12, 2,
  vs. the real 51). This is *why* three of them emit invalid Lua or
  nonexistent function calls — not carelessness, a missing feedback loop
  from the target API back into what gets emitted.
- The fix is mechanical, not a matter of trying harder: extract the real
  schema once, look everything up against it. That's this project.

## Functional dependency graph

Each row is a component. "Depends on" = must exist first. "Affects" = which
feature(s) break or can't start without it.

| # | Component | Depends on | Affects | Status |
|---|---|---|---|---|
| 1 | **Schema extractor** — reads `hl.meta.lua`'s LuaLS annotations (`---@class`, `---@field`, `---@alias`, `---\| "literal"`) into a queryable `Schema` object (classes/fields/types, aliases, config-key→type map) | nothing (reads the stub directly) | Validator, Converter — both are dead without this | **Done**, verified against the real installed stub (see `tests/test_extractor.py`) |
| 2 | **`luac -p` gate** (`hyprvalidate/luaast/luac_gate.py`) — shell out to `luac`, fail fast on invalid Lua before any schema-aware checking runs | nothing (just a subprocess call) | Validator (first/cheapest check), Converter (must run on its own output before calling a conversion done) | **Done** — `tests/test_luac_gate.py`, 3/3 passing. Exists as its own row because every one of the four existing tools skipped it and it alone would have caught 3 of 4 tools' fatal bugs |
| 3 | **Lua reader** (`hyprvalidate/luaast/reader.py`) — parses an *existing* `.lua` file into an AST, plus two schema-agnostic utilities the checker needs: dotted-name resolution (`hl.dsp.window.close` from a Name/Index chain) and scalar-literal resolution. Deliberately doesn't know about the schema or decide what's valid — that's row 4. | `luaparser` (PyPI, MIT, ANTLR-generated Lua grammar) — chosen over a hand-rolled parser after verifying it correctly parses this project's own real config (lambda-bodied binds, a `Fornum` loop, 101 real Call/Method nodes, working line numbers via `first_token.line`) | Validator only | **Done** — `tests/test_lua_reader.py`, 7/7 passing, includes a regression anchor against the real `hyprland-lua/keybinds.lua` |
| 4 | **Schema-driven checker** — walks the Lua reader's AST (3), cross-references every `hl.*` call and config key against the schema (1): unknown symbol, unknown key, wrong value type | 1, 3 | Validator — this is the Validator's actual logic, the other rows are plumbing around it | Not started |
| 5 | **Hyprlang reader** — lexer + parser + AST for the *old* `.conf` format (adapting hyprconf2lua's `lexer.py`, MIT-licensed, per `reference-tools/README.md`) | nothing new (adapts existing prior art) | Converter only — Validator never touches hyprlang | Not started |
| 6 | **Lua writer** — AST node types + emitter (AST → Lua text); shares node definitions with the reader (3) where the grammar overlaps | nothing new | Converter only | Not started |
| 7 | **Schema-driven mapper** — hyprlang AST (5) → Lua AST (6), deciding output symbol names and value types by looking them up in the schema (1) rather than a hardcoded table or string-sniffing the input | 1, 5, 6 | Converter — this is the piece that fixes the actual defect class found in all four existing tools | Not started |
| 8 | **CLI** — `hyprvalidate check <file.lua>` (needs 2, 3, 4) and `hyprvalidate convert <file.conf>` (needs 5, 6, 7, then 2 on its own output) | everything above, per subcommand | Both — this is just wiring, no new logic | Not started |

Read top to bottom for build order: **1 → 2 → 3 → 4** gets the Validator
shippable end to end without touching hyprlang at all. **5 → 6 → 7 → 8**
(converter half of 8) is a separate, later track that only starts once the
Validator is real — it also becomes the Validator's own test oracle (convert
something, then validate what came out).

## What this project is

**A standalone product**, shipped and marketed as its own thing — not a
patch destined for someone else's repo. Any future PR into one of the four
existing tools (e.g. wiring this schema into hyprlang2lua's emitter) is a
separate, optional action taken later, on its own merits, if it ever makes
sense — it is not this plan's goal or trajectory. Don't frame roadmap items
as leading toward "and then we contribute it upstream."

## Non-goals (for now — revisit if this doc gets updated)

- Not building a 5th end-to-end converter's *input* side from scratch — row
  5 explicitly reuses existing prior art rather than reinventing hyprlang
  parsing, which multiple existing tools already handle competently.
- Not distro-packaging or CI yet — no users until rows 1–4 exist.
