# How hyprvalidate compares — and what it owes to the tools before it

Every number on this page is measured, not asserted. `docs/measure_comparison.py`
reproduces all of them from the tools' own source; instructions are at the
bottom. If a number here is wrong, that's a bug — please open an issue.

This page exists because "trust me, mine is better" isn't an argument. It is
not a scoreboard: the tools below are the reason this project knows what the
problem *is*.

---

## Credit first, because it's owed

**[hypr2lua](https://github.com/Phillezi/hypr2lua) had the right idea before
this project existed.** It is the only pre-existing converter that tries to
read Hyprland's own autogenerated API stub instead of hardcoding a name table.
That idea — *ask the compositor what its API actually is* — is the entire
foundation hyprvalidate is built on. It arrived at it first. Its schema loader
doesn't currently work (see below), but the architecture around it is sound:
a real typed Lua AST, a proper emitter, schema threaded through the pipeline.

**[hyprconf2lua](https://github.com/Prateek-squadron/hyprconf2lua)** has by a
wide margin the most complete hyprlang coverage of any of these tools, and its
hyprlang lexer is genuinely good — good enough that **hyprvalidate adapted it**
(MIT, attributed in `hyprvalidate/hyprlang/lexer.py`) rather than writing a
worse one. Backslash continuation, `${}` expansion, and comment handling were
already correct there.

**hyprlang2lua** is the only one of the four whose output parses as valid Lua
on the test config, and it marks conversions it isn't sure about instead of
silently guessing — the behaviour this project considers non-negotiable.

**[hypr-migrate](https://github.com/loeclos/hypr-migrate)** carries the most
careful source-location and annotation tracking of the group, and it had the
right instinct about section handling (a `KNOWN_SECTIONS` whitelist) even
though it isn't wired into the emit path.

Reading all four is what made the actual defect *class* visible. That's not a
small debt.

---

## The one thing all of them share

Hyprland ships a machine-readable description of its entire config API:
`/usr/share/hypr/stubs/hl.meta.lua`, autogenerated from the compositor's own
source on every build, installed since the first Lua-capable release. It lists
every dispatcher, every config key, and every value type.

Each existing tool instead carries a **hand-written table** of that same
information, transcribed by a human from the docs. Hand-written tables drift
from the thing they describe. That's not carelessness — it's a missing
feedback loop.

### Measured: dispatcher coverage

| | dispatcher names known |
|---|---|
| Hyprland's actual API | **51** |
| hyprconf2lua (`DISPATCHER_MAP`) | 53 |
| hypr2lua (`bind.go` switch cases) | 11 |
| hypr-migrate (`_DISP_MAP`) | 2 |
| **hyprvalidate** | **0 hardcoded** — resolved from the stub at runtime |

Note hyprconf2lua's 53 against a real 51: a hand-maintained table can drift in
*both* directions. Being "more complete" than the API is its own bug — those
extra names don't exist to dispatch to.

### Measured: the schema that gets loaded but never read

hypr2lua loads the stub and threads a `Schema` object through its whole
pipeline. Replicating its parser (`pkg/lua/stubs/parser.go`) line-for-line
against the real file:

```
lines in hl.meta.lua                : 1778
discarded by the '--' prefix check  : 1736
entries actually registered         :    0
```

The cause is one line — `parser.go:29`:

```go
if line == "" || strings.HasPrefix(line, "--") {
    continue
}
```

In a LuaLS stub, `---@class` / `---@field` **are the data**, and they all start
with `--`. So every meaningful line is skipped as a comment. The 42 survivors
are `local __HL_X = {}` declarations, which its `registerPath()` then rejects
for having a single-segment path. The `Schema` object stays empty and nothing
downstream notices.

This is a one-line bug in an otherwise well-structured tool. It is also the
single clearest demonstration of why this project exists: *the schema was right
there, and reading it correctly is the whole job.*

### Measured: does the output parse?

`luac -p` on each tool's output for the same real 527-line `hyprland.conf`:

| tool | result |
|---|---|
| hyprlang2lua | **passes** |
| hyprconf2lua | fails — `:16: unexpected symbol near '='` |
| hypr2lua | fails — `:9: '}' expected (to close '{' at line 8)` |
| hypr-migrate | fails — `:43: '}' expected (to close '{' at line 41)` |

Three of four produce output Hyprland cannot load at all. A `luac -p` call is
about five lines of code and would have caught every one of these before
release — which is why it's a mandatory gate in hyprvalidate, run on the
converter's own output before anything is written to disk.

### Measured: a rename table that drifted

hypr-migrate's bind-flag table (`FLAG_MAP`):

```python
"l": "locked", "r": "repeat", "e": "longpress",
```

In real hyprlang, `r` is **release** and `e` is **repeat**. Both are wrong, in a
way that silently changes what your keybinds do rather than failing loudly.

This project hit the *identical* class of bug during its own development — an
early version emitted `{ mouse = true }`, copied from an example, when
`HL.BindOptions` has no `mouse` field at all. The difference is that
hyprvalidate's rename tables are **checked against the schema by its test
suite**, so a wrong target fails CI instead of shipping:

```python
def test_every_bind_flag_rename_target_is_a_real_bindoptions_field():
    for old_flag, field_name in BIND_FLAG_RENAME.items():
        assert field_name in schema.classes["HL.BindOptions"].fields
```

Hand-maintained knowledge isn't avoidable on the input side — hyprlang's old
names genuinely aren't in the new schema. What's avoidable is letting it drift
unchecked.

## What hyprvalidate does differently

| | others | hyprvalidate |
|---|---|---|
| Source of API names | hand-typed table | read from `hl.meta.lua` at runtime |
| Syntax gate on output | none (3 of 4 emit invalid Lua) | `luac -p`, mandatory, before writing |
| Validates its own output | no | yes — full schema check before success |
| Validates a config you already have | no tool does this | `hyprvalidate check` |
| Unsure conversions | mostly silent guesses | `-- TODO(hyprvalidate convert):` comment, never a guess |
| Output shape | one flat file | `--split` into a modular directory |
| Rename tables | unverified | asserted against the schema in CI |

The validator half has no equivalent in any existing tool: none of them can
tell you whether a Lua config you already have is valid.

## Reproduce it yourself

```bash
git clone https://github.com/Paritsingla7/hyprvalidate && cd hyprvalidate
mkdir -p reference-tools && cd reference-tools
git clone https://github.com/Prateek-squadron/hyprconf2lua
git clone https://github.com/Phillezi/hypr2lua
git clone https://github.com/loeclos/hypr-migrate
cd ..
python docs/measure_comparison.py
```

Anything it can't find it reports as "not measured" rather than guessing. The
`luac -p` results need each tool run against the same input config; the sample
outputs used above were produced from the 527-line `hyprland.conf` now vendored
at `tests/fixtures/hyprland.conf`.

## Scope and fairness

- Measured at the commits current as of 2026-08-11. These are moving projects
  and any of this can be fixed upstream at any time — if it has been, the
  numbers here are stale and I'd like to know.
- "Dispatcher coverage" counts distinct old dispatcher names each tool can
  translate. It is a proxy for completeness, not a quality score.
- hyprvalidate is younger and narrower than some of these. It does not attempt
  to be a drop-in replacement for every feature they have.
- No claim here is about the people who wrote these tools. They shipped working
  software into a community that needed it, and did it first.
