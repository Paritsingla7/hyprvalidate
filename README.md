# hyprvalidate

A converter and validator for Hyprland's Lua config format — both checked
against Hyprland's own authoritative, autogenerated API schema, not a
hand-typed guess.

```
$ hyprvalidate convert hyprland.conf --split ~/.config/hypr
wrote 10 file(s) to /home/you/.config/hypr/ (entry point: hyprland.lua)
  appearance.lua
  autostart.lua
  devices.lua
  ...

$ hyprvalidate check ~/.config/hypr
3 file(s) checked, no issues found.
```

**[Try it in your browser](https://paritsingla7.github.io/hyprvalidate/)** —
runs the real converter and validator against a frozen schema snapshot, no
install needed.

## Why

Hyprland moved from the old `hyprland.conf` (hyprlang) format to a Lua-based
config. Migrating an existing config means either hand-translating it or
using one of a handful of community converters — and testing all four found
that three produce output that doesn't even parse as valid Lua, and all four
independently hand-transcribe Hyprland's dispatcher and config-key names
into their own tables, which drift from reality (measured: one tool's
dispatcher table has 53 entries, another 12, another 2 — against the real
count of 51).

Hyprland already ships the real answer: an autogenerated LuaLS type stub
(`hl.meta.lua`) containing every valid config key, its type, and every valid
dispatcher function — regenerated from source on every build, installed
alongside the compositor since the first Lua-capable release. One of the
four existing tools already tries to read it and fails silently (its parser
extracts zero entries — confirmed by reading its source). None of the others
attempt it at all.

hyprvalidate reads that schema properly and uses it — instead of a
hand-maintained table — to convert old configs and check Lua ones.

## What it does

**Convert** an old `hyprland.conf` into Lua. Symbol names, value types, and
config keys are looked up in the schema instead of guessed from the input
string or hand-typed into a table. Anything the converter can't resolve
confidently becomes a `-- TODO(hyprvalidate convert): ...` comment, never a
silent guess. `--split` writes a modular directory (one file per config
area — monitors, keybinds, window rules, etc, the same pattern Hyprland's
own config docs recommend: "you can (and should!!) split this configuration
into multiple files... require them") instead of one flat file, with a
`hyprland.lua` entry point that `require()`s the rest.

**Check** an existing Lua config — hand-written, converted by this tool, or
output from anything else — against the real API: unknown dispatchers, bad
config keys, wrong value types, bad call arity, invalid fields inside a
`hl.monitor`/`hl.device`/`hl.bind`/etc spec table. Runs `luac -p` first as a
syntax gate.

The converter runs the checker on its own output before reporting success —
if a conversion doesn't validate cleanly, you see why immediately rather
than finding out when Hyprland reloads.

```
$ hyprvalidate check somebody-elses-converted-config.lua
somebody-elses-converted-config.lua:472: [type_mismatch] 'animations.enabled' expects boolean, got string ('yes, please :)')

1 issue(s) found.
```

## Structure

```
hyprvalidate/
  hyprvalidate/             the package
    schema/                 extractor: hl.meta.lua -> queryable schema
    hyprlang/                lexer + parser for the old .conf format
    luaast/                  Lua reader, writer, and the luac gate
    converter/               dispatch/coercion/rename tables/TODO emission/mapper
    checker.py               schema-driven checker - the Validator's logic
    cli.py                   `hyprvalidate check ...` / `convert ...`
  tests/
  docs/
    PLAN.md                 the build plan - what, why, dependencies
    CONVERTER_PLAN.md        the converter's design record
  site/                     the project site (GitHub Pages) - runs the real
                              converter/checker in-browser via Pyodide,
                              against a frozen schema.json snapshot
  schema.json                the frozen snapshot the site's demo loads -
                              regenerate with `hyprvalidate.schema.extractor`
                              against a current install if the schema changes
```

## Usage

Two ways to install, both verified against this repo:

**pipx (recommended, no clone needed):**
```
pipx install git+https://github.com/Paritsingla7/hyprvalidate.git
hyprvalidate convert path/to/hyprland.conf --split ~/.config/hypr
hyprvalidate check path/to/hyprland.lua [more-files.lua ...]
```
Isolates it in its own environment automatically. If `pipx` itself isn't
installed: on Arch, `pip install pipx` is blocked by default (PEP 668 -
system Python is externally managed) — use `sudo pacman -S python-pipx`
instead, or install `pipx` inside a venv.

**git clone + pip:**
```
git clone https://github.com/Paritsingla7/hyprvalidate.git
cd hyprvalidate
pip install .          # or: pip install -e .   (editable, for development)
hyprvalidate convert path/to/hyprland.conf --split ~/.config/hypr
hyprvalidate check path/to/hyprland.lua [more-files.lua ...]
```
On Arch/externally-managed Python, do this inside a venv
(`python3 -m venv .venv && .venv/bin/pip install .`) rather than passing
`--break-system-packages`.

### `convert`

```
hyprvalidate convert <file.conf> [-o output.lua] [--split DIR] [--stub PATH]
```

- No flags: prints the converted Lua to stdout.
- `-o FILE`: writes the converted Lua to `FILE` instead.
- `--split DIR`: writes a modular directory instead of one file — a
  `hyprland.lua` entry point plus one file per config area, matching how
  Hyprland's own docs recommend organizing a Lua config.

Exit codes: `0` clean, `1` the converted output has schema findings (this
can legitimately reflect an ambiguous value in your *original* config, not
a converter bug), `2` the input file failed to parse, the schema stub is
missing, or the converter's own output failed to produce valid Lua (that
specific case is always a converter bug — please report it).

### `check`

```
hyprvalidate check <file.lua|dir> [more...] [--stub PATH]
```

Accepts individual `.lua` files or a directory (checks every `.lua` file
inside it) — so you can point it straight at a `--split` output directory.

Exit codes: `0` clean, `1` schema findings, `2` invalid Lua or a missing/bad
`--stub` path.

Both commands accept `--stub /path/to/hl.meta.lua` if your install keeps the
schema stub somewhere other than the default.

## Requirements

- A Hyprland install with the Lua config API (v0.55+) — the schema is read
  from `/usr/share/hypr/stubs/hl.meta.lua` by default (path can be overridden).
- Python 3.10+.
